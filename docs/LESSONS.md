# 教訓 · 出過的錯與它們留下的規矩

這份文件只收**真的發生過**的錯誤。每一條都有：症狀、根因、留下的規矩，
以及**哪一支測試在守它** —— 沒有測試守著的教訓，下一個人（或下一次的我）會再犯一次。

寫在這裡而不是寫在 commit 訊息裡，是因為 commit 訊息沒有人會回頭翻，
而這些錯誤的共同點是：**它們都不報錯**。

> 新增條目時請一併補上「守門的測試」。如果那一欄填不出來，
> 表示這個教訓還沒有真的被固定下來，只是被記錄下來。

---

## L-001 空集合會把「壞掉」判成「完成」

**症狀（使用者回報）**：「輪練點了沒反應」＋「為什麼會自動跳很多輪？」

**根因**：判斷一輪走完沒，寫的是

```js
if (round.pos < round.queue.length) return round;   // 還沒走完，繼續用
// 走完了 → 開下一輪，輪數 +1
```

`queue` 是空的時候，`0 < 0` 為 false —— 於是**壞掉的輪次被判成走完的輪次**：

```
按一下 → 判定「走完了」→ 重建一輪、roundNo +1 → 發出一組空的牌
       → items.length === 0 → 停在「沒有符合的內容」（看起來像沒反應）
```

只要有過一次建輪撈不到內容（登入還沒接上就按下去就會這樣），
就存下一個 `queue: []`，之後**每按一次都 +1 輪**。
線上實際狀態：韓文站某使用者 `round_no=17`，而 `pos` 只有 `70/801` —— 一輪都沒走完。

**為什麼難發現**：「完成」與「無效」在數學上長得一樣（都讓 `a < b` 為假），
語意卻相反 —— 完成該前進，無效該原地修好。混為一談時，
**修復動作本身在推高計數**，而且全程不報錯。

**規矩**
- 判 `isComplete` 之前先判 `isUsable`（集合非空）。兩者是兩個具名函式，不准合成一個比較式。
- 產生集合的那一步撈到空就 `throw`，**絕不把空集合存成狀態** —— 存下去它會被下一次讀成「該換下一輪」。
- 修復路徑不得遞增任何計數。

**守門的測試**：`tests/round.test.mjs`【空的 queue 不是「走完」】
（已用種回舊邏輯的方式證明會紅 4 條）

## L-002 發牌不是消費

**症狀**：多按幾次輪練，詞庫就被吃掉幾十個，那些詞這一輪再也不會出現。

**根因**：指標在**發牌時**就前進（`r.pos += take.length`），
當時的理由寫在註解裡：「中途離開也算走過，否則同一組會無限重來」。

**為什麼錯**：使用者重按，是因為介面沒有給回饋（建一輪要撈 801 條，約 1 秒）。
也就是說 —— **系統懲罰了因為自己沒給回饋而產生的重試**。
而輪次池對使用者只有一個承諾：「每個詞這一輪都輪得到」，樂觀推進直接違背它。

使用者的原話定義了語意：
> 這個輪練是只有當這個池子裡的單詞全部**被消費完**了之後，才算是完成一輪。

消費＝答完，不是發出去。

**規矩**
- 凡是「拿一批出來做」的池子，指標一律在**完成回呼**裡推進（`onFinish` → `commitRound()`），讓重按天然冪等。
- 「中途離開怎麼辦」的正確答案是「下次拿到同一組」，不是「算他走過」。
- 待結算的數量由 `begin()` 統一持有（`roundOf` 參數），其他入口不傳就自動歸零 ——
  逐一在各入口清的話，漏掉一條路徑不會報錯，只會讓複習做完時去推進輪次池。

**守門的測試**：`tests/round.test.mjs`【發牌不是消費】【每個詞這一輪都輪得到】

## L-003 為使用者省一次點擊，不能拿走他的退路

**症狀（使用者回報）**：「刷新页面后……无法回到首页，这是非常严重的 bug」

**根因**：兩個「貼心」設計疊在一起：

1. 分頁列的「首頁」被改成 —— 有進行中的一輪就跳回那一輪（少按一下）
2. 開場不看網址，有做到一半的一輪就直接彈進學習畫面（少閃一下首頁）

單獨看都合理。疊起來的結果是：重新整理 → 被彈進學習畫面 →
按「首頁」→ 又被彈回學習畫面。唯一的出口是學習畫面裡那顆 🏠，沒有人找得到。

**規矩**
- **導覽列是使用者對「我能去哪」的唯一保證，不准有任何條件式攔截。**
  按「首頁」就是去首頁。
- 開場一律落在網址（hash）指定的那一頁。網址是使用者唯一能表達「我要去哪」的方式。
- 「接回上一輪」這種便利功能放在**畫面上的按鈕**（首頁那顆「繼續這一輪（還有 N 題）」），
  由使用者決定要不要用 —— 而不是把它綁進導覽行為裡。
- 通則：**便利功能不得覆蓋導覽意圖**。省一次點擊的代價若是「可能出不來」，那就不划算。

**守門的測試**：`tests/arch.test.mjs`【導覽列不准攔截】、
`tests/dom.test.mjs`、`tests/flow.test.mjs`【點「首頁」就去首頁】
（arch 那道已種壞樣本證明會紅）

## L-004 驗不到的程式碼就是會壞的程式碼

L-001 與 L-002 的規則原本都寫在 `shared/js/app.js` 的 `ensureRound()` 裡。
那個檔案碰得到 supabase 與 DOM，所以**沒有任何測試跑得到它** ——
而那正是這兩個 bug 活到線上的原因。

**規矩**
- 業務規則一律抽成純函式模組（本次抽出 `shared/js/study/round.js`：進去是狀態、出來是狀態，沒有 I/O）。
- `app.js` 是接線檔。它裡面出現的判斷式，等於是沒有測試的判斷式。
- 抽出來之後補一道 arch 閘門，擋住規則「漂回去」。

**守門的測試**：`tests/arch.test.mjs`【輪次池的規則不准回到 app.js】（已種壞樣本證明會紅）

## L-005 測試會挑時間騙人

`tests/card.test.mjs` 用 `new Date().toISOString().slice(0,10)`（**UTC 日期**）組 localStorage 的鍵，
而程式在 `3e7210a` 之後改用 `dayKey()`（**本地日期**）。

在 UTC+8，只有**午夜到早上八點之間**兩者才會差一天。
於是這條測試白天跑永遠是綠的，半夜跑才紅 —— 而它紅的時候，看起來像是「剛剛改壞了」。

**規矩**
- 測試取鍵、取路徑、取設定，一律走**正式路徑的那支函式**（`lsKey()`、`dayKey()`），不准自己重組。
  自己重組的話，程式改了實作，測試會去讀一個沒人寫的格子，而斷言仍然「通過」——驗的是空氣。
- 跟時間有關的測試，至少換一個時區再跑一次（`TZ=UTC`、`TZ=Pacific/Kiritimati`）證明不是碰巧。

## L-006 用 `tail` 截斷輸出來下結論

檢查日文站的 migration 狀態時跑了 `... | tail -4`，
剛好把「待套用」清單截掉，於是把 **待套 2 個** 讀成 **全部已套用**。

實際狀態是：日文站缺 `0021_log_review_atomic`，也就是缺 `log_review` 這支 RPC。
而當時工作區有一份未提交的 `progress.js` 正是呼叫它 ——
推上去的話，**日文站每次答題都會「儲存失敗」**。

**規矩**
- 判斷「有沒有待辦」的輸出不准截斷。要短就用 `grep -A99 '待套用'`，不要用 `tail -N`。
- 台帳（`schema_migrations`）說「已套用」不算證據。**驗實際狀態**：
  用 PostgREST 的 OpenAPI 列出真的存在的 RPC，逐站比對前端用到的那幾支。

  ```bash
  # 兩站都要跑，並印出 project ref
  curl -s -H "apikey: $KEY" -H "Accept: application/openapi+json" "$SUPABASE_URL/rest/v1/" \
    | python3 -c "import json,sys; print(sorted(p[5:] for p in json.load(sys.stdin)['paths'] if p.startswith('/rpc/')))"
  ```
- 兩個 Supabase 專案的 migration 會漂移。**推任何呼叫新 RPC 的前端程式之前，逐站確認那支 RPC 真的在。**
  前端是共用的，資料庫不是 —— 這是 monorepo 最容易出事的接縫。

## L-007 兩個症狀不代表兩個 bug

使用者分兩次回報「點了沒反應」與「輪數自動跳」，聽起來是兩件事。
實際上是同一行程式碼的兩個出口（見 L-001）。

**規矩**：修之前先把**線上真實資料**撈出來看（`study_rounds` 的 `round_no` / `pos` / `queue` 長度）。
`round_no=17` 配上 `pos=70/801` 這個組合，一眼就指出「輪數的推進與 pos 無關」，
而那直接鎖定了根因。從症狀猜根因會猜出兩個修法，從資料看只會看到一個。

## 通則

這七條的共同點：**全部都不報錯**。

- 空輪次不報錯，它只是靜靜地讓輪數往上跳
- 樂觀推進不報錯，它只是讓詞悄悄消失
- 導覽攔截不報錯，它只是讓人出不去
- 截斷的輸出不報錯，它只是把「有待辦」顯示成「沒待辦」
- 挑時區的測試不報錯，它白天還會給你一個綠勾

所以規矩不是「更小心」，而是：
**任何「無輸出／無異常即通過」的檢查，都要先造一個壞樣本證明它會報警。**
本次新增的每一道閘門都做了這件事（見各條的「守門的測試」）。
